# 超级学霸桌面统一发行

目标是新用户安装当前完整版本，已有用户从“核心 → 检查更新”或“设置 → 关于 → 检查更新”取得后续优化。Windows x64、Intel Mac x64、Apple 芯片 Mac arm64 同时成立；不能把源码提交、单平台成功或只发布核心当作完成。

## 先确认本批与所有者

- 在项目 AGENTS.md、CURRENT-DESKTOP-RELEASE.json 和现行 GitHub Latest/稳定清单间核对真实基线；目录名、较新的源码分支和候选 Release 不等于已发布。当前发行仓库为 1281504089-cell/kaixin-k12-tutor，以工具和实际配置复核。
- 用项目 .local/desktop-release-in-progress.json 记录唯一合并/发布所有者、参与对话、候选、阶段及授权输出。其他发布已进行时先读状态，避免抢清单或重复晋升。
- 用户授权跨对话协调后，只联系本批指定对话，收集冻结源码、父基线、补丁/资源/前端摘要、已发布与未发布范围、验收回执和未验项。默认排除用户所称“图像优化”及其显示名“图像生成优化”的同一对话；未经另行授权不向其派任务或催交接。
- 其他对话继续完成当前验证并交接，最终由发布所有者合并和切入口。用户要求等齐时，不提前把某一单项设成最新版。不因暂存未验项覆盖其他已发布修复。

## 核心更新与启动器分开判断

- 每项改动识别其载体：学习核心/前端、教材、本机依赖、桌面更新器/Electron、图标与系统权限声明。在线清单必须真的携带所需载体；只换 core/web 不会修复旧启动器。
- 默认交付应让用户点击“检查更新”完成下载、校验、备份、切换和重开。离线 .command/.cmd、选 JSON、开发终端命令不能成为日常升级步骤。
- 涉及更新器、图标、原生依赖或权限声明时，核对客户端是否能通过现有更新入口升级这些部分。不能发布一个核心包就声称更新器/应用外壳已更新，也不能默认旧电脑都已有新外壳。
- 对无法靠旧更新器自行修复的历史版本，先验证是否能安全复用已有依赖。若确需一次性启动器/兼容包迁移，按用户已允许的例外明确给出三个系统的文件、适用旧版本、保留的数据及迁移后的正常更新入口；不用模糊的“已兼容所有版本”掩盖。完成迁移后验证再次“检查更新”正常，后续优化不重复要求手动补丁。
- 本次旧版迁移完成后，不能把再次人工迁移作为日常方案。后续改动若超出现有在线更新载体，先补齐并验证三端在线升级能力，或保留为未发布候选；不把需要另装补丁的优化宣称为已完成交付。
- 不能通过删除学习目录、伪造运行环境编号、降低验签或关闭系统安全功能来实现兼容。

## 冻结与真实升级验收

- 从当前成功基线在独立目录合并，保留已验收功能和本批前已发布的修复；不能整份覆盖共享文件。记录一个冻结学习源码/前端、三个原生环境以及各启动器版本和逐文件摘要。
- 扫描实际支持的历史基线，包括早期完整版、新完整版、装过兼容运行包的版本、当前版及已做一次迁移的旧启动器。把每种组合写成升级矩阵，不能只测最新到最新。版本号相同的不同运行核心也要区分。
- 三个平台在各自原生环境验证：从公开 GitHub 安装文件下载齐并核对 SHA256、安装到空白目录、实际启动随包当前核心、教材原页/数量、中文界面和正常退出；已有合成聊天、任务、测试 Key、设置与阅读记录升级后保留。
- 验收更新入口的完整路径，覆盖检测、确认、下载、校验、备份、切换、重启、再次检查已是最新以及失败回退。下载清单成功、桥接包安装成功、静音测试或模拟界面都不能替代实际入口和相关真实功能。
- 网络验收覆盖公开匿名下载、系统代理/PAC、直链连接异常、HTTP 错误、断流/停滞、取消、截断/校验失败和磁盘错误。失败须有有限等待、可理解结果和残留清理；取消不自动重试，不能误删已有文件。
- Electron 与 Node 的网络实现和跳转行为不同；在实际打包的 Electron 中验证代理及每次跳转的受信来源限制。不要关闭 TLS 验证、给客户端放 GitHub Token、把整包缓存在内存，或把真实 API Key/学习数据放进安装包与公开日志。
- 更新慢先区分准备、下载、校验和重开，记录实际所选核心或兼容资源的字节数；百分比缓慢增长不能直接判为挂起。减少包体时只排除已查明无运行引用的开发文档资源，保留教材、原音、品牌、字体、许可证与所需依赖，并比较最终归档及实际升级结果。下载窗口属于旧外壳时，不能声称核心更新已为它增加总大小、速度显示或慢连接切换。
- 涉及后台上传、资料引用和附件预览时，在同一最终核心上实测上传中跨聊天与设置、追加文件、原件逐字节回读、草稿和来源项目保留及账号隔离。区分应用内部切页、退出后续传、系统语音接口和实际扬声器音频，未验证的能力不得写成已支持。
- 只复用文件摘要和调用关系均未变的验收证据。受影响逻辑、依赖或基线变化必须重测；失败不能删用例、放宽权限或仅改成“通过”。本机、原生 CI、用户实体设备的结果分开记录。

## 统一发布与读回

- 使用现有验签/三端批次门禁核对平台、架构、运行环境、冻结源码、版本时间及归档摘要。清单里的兼容分流也须签名，并与同批核心一致；单个默认清单不能同时假装匹配两个不同底座。
- 新归档先上传到独立候选，三端最终文件全部合格后才切稳定入口和 Latest。测试、签名、发布使用同一冻结字节；生产私钥留维护者本机。未知上传/晋升结果先读回，不盲目重发；别覆盖已发布且用途不明的版本。
- 发布后读回每个稳定清单、兼容清单与其实际归档，核对签名和 SHA256；再用受支持旧客户端确认能发现并取得对应版本。GitHub 改源码不会自动把修改送到用户电脑。
- 完整包、在线更新、必要的一次性迁移包必须属于同一个最终相容批次，不能让新用户还需拼装数个手动补丁。必要迁移应单独说明，不反复改变普通用户入口。
- 源码补丁链和版本说明要能重建实际发行内容。最终 CURRENT-DESKTOP-RELEASE.json 记录 GitHub tag/commit、学习核心、启动器、三端环境与归档摘要、签名清单、验收/发布回执、迁移例外和回退位置；仅在真实发布成功后更新指针。

## 授权的 U 盘替换

- 用户要求写盘时，先核对目标卷、可用空间、旧安装包清单及同盘其他资料摘要。只处理授权的超级学霸安装包范围，保留数学资料、个人文件、学习记录、设置和密钥。
- 按用户确认区分“从零安装”“装过前一个兼容补丁”“只有旧版、从未打补丁”三个入口，各覆盖三端。后两类直接使用本次合格迁移方案，不先补装旧补丁；若复用同一文件，说明按电脑情况任选一类，不能写成依次安装。所需原生资源可由检查更新自动补齐一次，并明确是否需要联网。
- U 盘优先提供每种 Mac 一份可直接打开的普通 DMG，Windows 一份包含 Setup 和全部 Runtime 分卷的完整 ZIP。容器可不同于 GitHub 分卷，但其中应用、核心与原生资源须与同批已验证文件一致。
- Windows 可流式复用旧 ZIP 中与当前正式清单大小、SHA256 完全一致的 Runtime，Setup 必须取当前批次，再完整读回新 ZIP 的成员、CRC 和摘要。Mac 先逐卷核对当前批次，再转换为普通单文件镜像，核对只读挂载、签名、架构与随包核心；单份合格即可顺序写盘，与下一份本地准备并行，保留足够临时空间，不展开整套应用占满磁盘。
- 新文件先完整写入暂存目录并回读 SHA256，验证 Mac 镜像/应用签名与 Windows 文件集合后再替换旧入口；新批全齐且回退证据保留后才清理明确被替代的旧安装包。不得先删旧包给未验新包腾位置。
- 安装说明只保留清楚的新装、检查更新和必要迁移路径。最终核对盘上其他资料未变，并记录实际释放空间与写盘回执。

交付时说清三端各自的可用版本、首次安装与检查更新是否真实通过、历史例外、GitHub 与 U 盘状态、未验实体设备范围。不能用大量单元测试数代替端到端证据。
